<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → /api/users | Untrusted JSON from an authenticated admin browser/native client |
| API → MySQL | Parameterized queries via mysql2 named placeholders |
| API → req.user | Authenticated subject — may attempt to act on their own row |

## STRIDE Threat Register (extends Phase 1 T-01-*)

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | E (Elevation) | /api/users routes | mitigate | `authMw + requireRole('admin')` applied at router level — single callsite, cannot be bypassed on any sub-route |
| T-02-02 | I (Info disclosure) | usersController responses | mitigate | Every response goes through `sanitizeUser`; `password_hash` never selected in findAll/findById; test helper scans every response body |
| T-02-03 | T (Tampering) | Password handling on create/update | mitigate | `hashPassword` (bcrypt rounds=10) is the only code path that materializes `password_hash`; controller never writes plain password to the DB |
| T-02-04 | D (Denial of service) | Admin locks self out by deactivating own account | mitigate | Controller compares `req.user.id === Number(req.params.id)` before calling `setActive` — returns 409 self_lockout_forbidden |
| T-02-05 | T (Tampering) | Permission strings in request body | mitigate | `isValidPermissionArray` rejects anything not in the canonical list or `'*'`; returns 400 invalid_permissions |
| T-02-06 | I (Info disclosure) | Username enumeration via create / update | accept | Returning 409 `username_taken` confirms existence of a username, but the endpoint is already admin-only — admin has LIST access anyway, so no additional leakage |
| T-02-07 | T (Tampering) | Role field accepts arbitrary string | mitigate | `VALID_ROLES = ['admin', 'staff']` whitelist; 400 invalid_role otherwise |
| T-02-08 | S (Spoofing) | A freshly-deactivated user keeps their JWT valid | mitigate | Inherits Phase 1's `authMiddleware` DB re-query — next request with that token returns 401 immediately (no code change needed here, but explicitly depended upon) |
| T-02-09 | T (Tampering) | SQL injection via update/list paths | mitigate | mysql2 named placeholders only; no string concatenation into SQL; `update()` whitelists allowed keys before building the SET clause |

No new CORS, no new cookie surface, no new rate limits (reuse Phase 1's `helmet`, `cors({ credentials:true })`, and JSON body size cap).
</threat_model>
